## 기능을 제공하는 것과, 확인할 수 있게 하는 것은 달랐습니다

2022년 4월부터 2023년 8월까지 다우기술에서 키움저축은행 차세대 소비자금융 리뉴얼에 참여했습니다. 전체 24명 규모 프로젝트에서 제가 맡은 역할은 공통파트 PL이었습니다. 프로젝트 전체를 총괄한 것이 아니라, 업무 개발자가 사용할 공통 기능과 개발·운영 기반을 담당했습니다.

그중 외부기관 전문 연동에서는 기능 구현 외에 풀어야 할 문제가 있었습니다. 서버 대 서버 통신 제약 때문에 개발자 PC에서 외부기관으로 직접 요청을 보내기 어려웠습니다. 업무 코드를 수정해도 결과를 확인하려면 서버 배포를 거쳐야 하는 상황이었습니다.

제가 바꾸려 한 것은 외부기관의 통신 제약 자체가 아니었습니다. **그 제약 아래에서도 개발자가 로컬에서 연동 결과를 확인할 수 있는 경로**였습니다.

## 업무에서 보내는 내용과, 실제 보내는 경로를 나눴습니다

같은 프로젝트에서 전문 송수신부와 조립·분해 책임을 구분하고, 기존 송신 로직을 수신 소켓 서버에서도 재사용할 수 있도록 구조를 정리했습니다. 로컬 테스트 문제에는 송신 기능을 추상화하고 실행 환경에 따라 송신 경로를 달리하는 방식을 적용했습니다.

로컬·개발·운영 profile을 분리하고, 로컬에서는 개발 서버를 경유해 송신 API를 호출하도록 구성했습니다. 개발자 PC가 외부기관에 직접 접근하는 대신, 개발 서버를 거치는 경로에서 전문 송수신을 확인할 수 있게 한 것입니다.

```text
로컬 테스트 경로의 개념도

개발자 PC에서 실행하는 코드
    → 개발 서버의 송신 API
    → 외부기관과 전문 송수신
    → 로컬에서 결과 확인
```

이 개념도에는 제가 구성한 로컬 테스트 경로의 역할과 흐름만 요약했습니다. 실제 네트워크 구성도는 아닙니다.

## 개발 서버를 거치는 선택에는 확인 범위의 한계도 있습니다

현재 관점에서 이 선택을 다시 설명하면, 모든 환경을 같게 만드는 대신 **로컬에서 확인할 수 있는 범위를 넓힌 것**입니다. 개발 서버를 사용하므로 완전히 독립적인 로컬 테스트 환경이 된 것은 아닙니다. 서버 상태와 외부기관의 응답 조건에도 영향을 받는 경로입니다.

반대로 로컬 테스트만으로 운영 환경의 모든 조건을 검증했다고 볼 수도 없습니다. 경로를 제공했다는 사실과, 그 경로로 어느 조건까지 확인했는지는 별도로 설명해야 합니다.

## 결과는 배포를 거쳐야 했던 확인 경로를 바꾼 것입니다

개발자 PC에서도 서버와 유사한 환경으로 전문 송수신을 테스트할 수 있도록 구성했습니다. 이를 통해 연동 기능을 확인할 때마다 서버에 배포해야 하는 비효율을 줄였습니다.

대기 시간이나 테스트 횟수의 전후 측정값은 제시하지 않습니다. 수치화한 개선율 대신 **어떤 반복 작업을 줄일 수 있게 되었는지**로 이 변경의 결과를 설명합니다.

## 공통 기능의 사용자는 같은 프로젝트의 개발자였습니다

이 경험을 통해 공통파트의 산출물을 기능 목록으로만 설명하지 않게 되었습니다. 호출할 수 있는 기능을 만드는 일과, 다른 개발자가 자신의 변경을 확인할 수 있게 하는 일은 연결되어 있었습니다.

지금 비슷한 기반을 설계한다면 다음 세 질문부터 확인하고 싶습니다.

- 업무 로직을 바꾸지 않고 환경별 실행 경로를 구분할 수 있는가?
- 개발자가 직접 확인할 수 있는 범위와 서버에서만 검증할 범위가 명확한가?
- 공통 경로가 실패했을 때 어느 구간의 문제인지 구분할 수 있는가?

이 질문들은 현재의 설계 기준이며 당시 모든 항목을 검증했다는 뜻은 아닙니다. 이 프로젝트에서 가져온 핵심은 공통 코드를 얼마나 많이 만들었는가보다, **다른 개발자가 어떤 확인을 스스로 할 수 있게 되었는가**를 함께 설명하는 것입니다.
