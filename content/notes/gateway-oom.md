## Gateway의 장애를 요청 크기와 연결했습니다

MLOps 플랫폼 운영 중 External Gateway에 148MB의 대용량 요청이 들어왔고, Pod 3개 중 2개가 다운되는 OOM 장애가 발생했습니다. 저는 원인을 분석하고 Pod scale-out과 메모리 scale-up을 적용했습니다.

이 사례에서 중요한 것은 ‘서버가 다운됐다’는 증상에서 멈추지 않고, **어떤 요청 조건에서 어느 구성요소의 자원 문제가 발생했는지**를 구체화한 점입니다. 모델 자체의 추론 오류나 플랫폼 전체 장애를 같은 문제로 묶지 않았습니다.

## 요청의 크기와 프로세스의 메모리는 구분합니다

148MB는 당시 요청의 크기입니다. Gateway 프로세스의 최대 메모리 사용량, 설정한 메모리 제한, 모델 크기를 의미하지는 않습니다. Pod 3개 중 2개가 다운됐다는 사실도 요청 실패율이나 전체 플랫폼 가용성의 수치로 바로 환산할 수 없습니다.

| 확인한 사실 | 대응의 범위 |
|---|---|
| 대용량 요청 148MB | 요청 조건과 OOM 원인의 연결 분석 |
| Gateway Pod 3개 중 2개 다운 | Gateway의 Pod 수·메모리 자원 대응 |
| OOM 발생 | Pod scale-out과 메모리 scale-up 적용 |

실제 장애 로그·Heap Dump·프로세스 메모리 그래프는 이 글에 재현하지 않습니다. 요청 파싱이나 객체 복제로 메모리가 몇 배 늘었다는 세부 원인도 임의로 추가하지 않습니다.

## scale-out과 메모리 scale-up은 다른 조치였습니다

Pod scale-out과 메모리 scale-up을 함께 적용했습니다. 실행 인스턴스를 늘리는 변경과 인스턴스의 메모리 자원을 늘리는 변경을 같은 대응으로 뭉뚱그리지 않고 구분합니다.

조치를 설명할 때도 ‘Pod를 늘려서 해결했다’ 한 문장만으로 끝내지 않습니다. 요청 하나가 처리되는 데 필요한 자원과 Gateway가 요청을 받는 실행 구성을 함께 다룬 대응이기 때문입니다. 다만 두 변경의 효과를 따로 측정한 비교 실험이나 정확한 변경 전후 설정값을 이 글에 제시하지는 않습니다.

```text
장애와 조치의 개념도

148MB 대용량 요청 → External Gateway OOM
                         → Pod 3개 중 2개 다운

조치: Pod scale-out + 메모리 scale-up
```

이 그림은 요청 분산 정책이나 장애 당시의 전체 시간 순서를 재현한 것이 아닙니다. 원인 분석에서 확인한 조건과 적용한 자원 조치를 정리한 것입니다.

## 자원 조치가 모든 입력의 안전성을 보장하지는 않습니다

이 장애에서 OOM 원인을 분석하고 자원 대응을 적용했습니다. 이를 모든 요청 크기에 대한 안정성 보장이나 OOM 재발 0건이라는 결과로 확대하지 않습니다. 이후 요청량·메모리 사용량·장애율의 수치를 별도 근거 없이 추가하지도 않습니다.

응답 유실에 대한 재송신 로직이나 다른 구성요소의 장애 대응은 별도의 변경입니다. 이 사건에서 수행한 조치로 한꺼번에 묶지 않습니다.

## 다음에는 입력 조건도 운영 경계로 남기겠습니다

이 경험에서 얻은 기준은 API의 입력을 기능 계약뿐 아니라 자원 조건으로도 보는 것입니다. 같은 기능의 요청이라도 크기와 동시 처리 조건이 바뀌면 운영에서 다른 문제가 드러날 수 있습니다.

현재 다시 점검한다면 허용할 요청 크기, 동시에 처리할 요청 수, 메모리 관측과 초과 입력의 거부·분할 방식을 함께 검토하겠습니다. 스트리밍 처리나 요청 제한을 당시 구현했다는 주장은 아닙니다. 자원 확장 이후에도 무엇을 확인해야 하는지를 남기는 후속 기준입니다.
