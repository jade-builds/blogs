## 병렬 실행과 DB의 처리 경계는 함께 봐야 했습니다

키움저축은행 차세대 소비자금융 리뉴얼에서 공통파트 PL로 Spring Batch·Quartz 기반 배치 서비스 구성을 담당했습니다. 주요 배치의 처리량이 많았고, 순차 처리와 큰 트랜잭션 범위는 처리 지연과 DB Lock 경합을 함께 고려해야 하는 조건이었습니다.

이 작업에서는 ForkJoinPool 기반 병렬 처리와 고객 단위 트랜잭션 조정을 함께 적용했습니다. 중요한 질문은 스레드를 몇 개 늘릴지가 아니라, **무엇을 나눠 실행하고 어느 범위를 하나의 DB 처리 단위로 볼 것인가**였습니다.

## 실행을 나누는 단위와 완료를 묶는 단위는 다릅니다

ForkJoinPool은 작업 실행을 나누는 변경이었고, 고객 단위 트랜잭션은 DB 처리 경계를 조정하는 변경이었습니다. 같은 성능 개선 안에서 수행했지만 책임은 달랐습니다.

| 변경 축 | 제가 적용한 방향 |
|---|---|
| 배치 실행 구조 | ForkJoinPool 기반 병렬 처리 |
| DB 처리 경계 | 기존 큰 업무 범위를 고객 단위로 축소 |
| 함께 고려한 운영 조건 | DB Lock 경합과 부하, 배치 처리 시간 |

위 구분은 당시 변경의 역할을 설명한 것입니다. 스레드 수·커넥션 풀 크기·격리 수준의 설정값이나 실제 커밋 횟수를 뜻하지는 않습니다.

## 병렬화만의 결과로 설명하지 않습니다

병렬로 실행할 작업을 나누더라도 DB에서 묶는 범위를 그대로 두면 변경의 의미를 충분히 설명하기 어렵습니다. 저는 실행 구조를 바꾸는 작업과 고객 단위 트랜잭션 조정을 함께 수행했고, 주요 배치의 처리 시간을 **평균 28분 수준에서 9분대로 약 68% 단축**했습니다.

여기서 9분대를 정확한 9.0분으로 바꾸거나 개선율을 새로 정밀 계산하지 않습니다. 또한 두 변경의 효과를 따로 측정한 실험은 제시하지 않으므로 전체 개선을 ForkJoinPool 하나의 효과로 귀속하지 않습니다.

```text
변경 책임의 개념도

배치 작업 실행 → 병렬 처리로 실행 구조 변경
고객 업무 처리 → 고객 단위로 트랜잭션 경계 조정

두 변경을 적용한 주요 배치의 결과: 28분 수준 → 9분대
```

이 그림은 당시 스레드·트랜잭션 호출 경로나 전체 실패 처리를 재현한 것이 아닙니다. 실패 고객 재시도, 작업 중복 방지, 커넥션 풀 제한의 구체적인 구현은 이 글에 추가하지 않습니다.

## 개인정보 파기 배치와는 다른 경험입니다

2021년 개인정보 파기 배치에서는 고객별 반복 조회·DML을 단계별 통합 처리로 바꾸고 4시간을 1.5시간으로 줄였습니다. 이 글은 2022–2023년 차세대 리뉴얼의 주요 배치 개선이며, 접근과 수치가 다릅니다.

둘을 ‘배치 최적화’ 한 줄로 합치면 제가 바꾼 지점도 사라집니다. 파기 배치는 불필요한 반복 접근을 줄이는 구조 변경에, 이 배치는 실행의 병렬화와 DB 처리 경계의 조정에 초점이 있습니다.

## 다음 병렬화에서 확인할 기준

이 경험 이후에는 실행을 잘게 나누는 것과 데이터를 안전하게 처리하는 것을 같은 설정 문제로 보지 않습니다. 현재 다시 점검한다면 동시 작업 수와 DB 커넥션 사용량, 고객별 실패·재실행의 경계, 잠금 경합을 같은 흐름에서 확인하겠습니다.

이는 당시 모든 부하·실패 조건을 테스트했다는 주장이 아니라, 성능 개선을 다음 설계로 가져갈 때 더 분명히 남길 검증 기준입니다.
