## 요청을 보냈다는 사실과 결과를 받았다는 사실 사이에 문제가 있었습니다

MLOps 플랫폼 운영 중 APS 통합시퀀싱의 야간 요청 4건이 유실되는 문제를 분석했습니다. 확인한 원인은 async_response=false 상태에서 HTTP 202 응답을 최종 응답으로 오인하는 처리 흐름이었습니다. 저는 해당 false 처리 로직을 개선했습니다.

이 사례의 질문은 요청을 다시 보내는 방법이 아니라, **응답을 받은 뒤 어느 시점에 업무가 완료됐다고 판단하고 있었는가**였습니다. 요청 전송과 응답 수신만 보면 놓칠 수 있는 처리 경계였습니다.

## 최종 결과가 아닌 응답에서 처리가 끝나고 있었습니다

해당 경로에서는 async_response=false 조건인데도 HTTP 202 응답을 최종 응답으로 취급했습니다. 그 결과를 업무 완료로 해석하는 분기가 요청 유실 문제의 원인이었습니다.

| 확인한 항목 | 의미 |
|---|---|
| APS 야간 요청 4건 유실 | 원인을 분석한 업무 현상 |
| async_response=false | 문제가 발생한 처리 분기의 조건 |
| HTTP 202를 최종 응답으로 오인 | 잘못된 완료 판단 |
| false 처리 로직 개선 | 제가 변경한 지점 |

4건은 분석 대상 요청 수입니다. 전체 처리량의 분모가 없으므로 실패율로 환산하지 않습니다. 이 사건을 Kafka 메시지 유실, DB 저장 유실이나 모델 실행 실패로 바꿔 설명하지도 않습니다.

## 바꾼 것은 재시도 횟수가 아니라 완료를 해석하는 로직이었습니다

async_response=false에서 HTTP 202를 최종 응답으로 취급하던 로직을 개선했습니다. 이 글에서는 이후 결과를 받는 세부 방식이 폴링인지 콜백인지, 어떤 저장 상태를 거쳤는지 임의로 확정하지 않습니다. 해당 사건의 상세 구현과 플랫폼이 지원하는 다른 비동기 경로는 구분해야 합니다.

```text
문제가 된 완료 해석의 개념도

async_response=false 경로
    → HTTP 202 수신
    → 최종 응답으로 오인한 처리

변경: 해당 조건의 응답 처리 로직 개선
```

위 그림은 당시 코드나 전체 상태 머신의 재현이 아닙니다. 잘못된 완료 판단이 놓인 조건을 요약한 것입니다.

## 비동기 검증의 일반 원칙과 실제 결함을 구분합니다

기존 글 ‘배포 성공을 어디까지라고 부를 것인가’에서는 요청 접수와 업무 완료를 구분하는 기준을 설명했습니다. 이 글은 그 기준과 연결되지만, 실제 야간 요청 유실에서 어느 분기를 고쳤는지를 다루는 별도의 경험입니다.

플랫폼에서 수행한 비동기 콜백 검증이나 통신 실패 시 재송신 개선을 이 사건의 수정 내역으로 합치지 않습니다. 이번 작업의 결과는 확인한 응답 해석의 결함을 개선한 것이며, 전체 경로의 정확히 한 번 처리나 이후 유실 0건을 보장했다는 의미가 아닙니다.

## 다음에는 중간 응답과 업무 완료를 따로 확인하겠습니다

이 경험을 통해 정상 상태 코드 하나만으로 최종 성공을 표시하지 않는 기준을 더 분명히 갖게 됐습니다. 설정값의 이름보다 실제 분기에서 어떤 응답을 받아 어떤 상태로 끝내는지를 확인해야 합니다.

현재 이 경로를 다시 검증한다면 설정값별 중간 응답, 최종 결과, 타임아웃, 중복 응답을 나눠 확인하겠습니다. 이는 당시 모든 조합의 테스트를 완료했다는 주장이 아니라, 수정된 완료 판단을 다음 회귀 검증으로 확장할 때의 기준입니다.
