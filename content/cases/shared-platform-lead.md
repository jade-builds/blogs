## 공통 기능의 사용자는 같은 프로젝트의 개발자였습니다

다우기술에서 키움저축은행 차세대 소비자금융 리뉴얼의 공통파트 PL을 맡았습니다. 노후화된 내부 업무 시스템과 홈페이지를 새로 구축하는 프로젝트였고, 전체 참여 인원은 24명이었습니다. 제가 담당한 범위는 공통파트이며 전체 프로젝트 총괄은 아니었습니다.

전문 송수신, 인증, 프레임워크, 배포 기반을 만드는 일은 서로 떨어진 기능 목록처럼 보일 수 있습니다. 하지만 공통파트 관점에서는 하나의 질문으로 연결됐습니다. **업무 개발자가 어떤 기능을 재사용하고, 어디에서 자신의 코드를 개발·확인·배포할 수 있게 할 것인가**였습니다.

## 전문 종류가 늘어도 같은 책임을 복제하지 않도록 했습니다

외부기관과 채널 연계가 늘면서 전문 종류가 기존 대비 약 20~30배 증가했습니다. 기존 구조를 그대로 확장하면 조립·분해 로직과 기관별 처리의 중복이 늘어날 수 있었습니다.

저는 전문의 수신부와 송신부를 분리하고, 조립과 분해의 책임을 구분했습니다. 송신-수신 객체와 수신-송신 객체를 상속 구조로 나눠, 기존 송신 로직을 수신 소켓 서버에서도 재사용할 수 있도록 구성했습니다.

여기서 바꾼 것은 전문의 양식만이 아니었습니다. 어떤 방향의 요청을 받든 같은 책임을 다시 구현하지 않도록 재사용 지점을 정리한 것입니다. 20~30배는 대응해야 했던 전문 종류의 증가이며, 처리량이나 성능 개선 배수가 아닙니다.

## 인증 정보를 업무 코드마다 다시 해석하지 않게 했습니다

Spring Security·JWT·Refresh Token으로 로그인과 인증 유지 기능을 구현했습니다. 인증된 사용자 정보는 SecurityContextHolder·UserDetails 등을 통해 공통으로 활용할 수 있게 구성하고, Filter에서 요청 처리에 필요한 로그인 사용자 정보를 미리 제공했습니다.

업무 개발자가 각자 인증 객체를 반복 조회하거나 파싱하지 않아도 되도록 공통 사용 경로를 만든 것입니다. 전문 처리에서는 재사용할 책임을 나눴고, 인증에서는 업무 코드가 공통으로 사용할 정보를 제공했습니다.

| 공통파트의 변경 | 업무 개발자가 사용할 기반 |
|---|---|
| 전문 송수신·조립·분해 책임 분리 | 기존 전문 처리 로직의 재사용 |
| 인증 사용자 정보 공통 제공 | 업무별 반복 조회·파싱의 축소 |
| 환경별 profile·송신 경로 분리 | 개발 서버를 경유한 로컬 연동 확인 |
| 서비스별 배포 단위·브랜치 체계 구성 | 변경을 반영하고 배포하는 공통 경로 |

이 표는 구현한 기반의 역할을 정리한 것입니다. 모든 개발자가 사용한 횟수나 생산성 개선율을 측정한 결과는 아닙니다.

## 공통 코드는 배포와 운영의 경계까지 필요했습니다

소비자금융 메인, 전화교환, 배치, 대고객 홈페이지를 서비스 성격에 따라 분리 구성했습니다. 기능을 나누는 것에 그치지 않고 배포 단위와 장애 영향 범위를 줄이려는 방향이었습니다.

형상관리는 메인 브랜치·업무 PL 브랜치·개발자 브랜치의 3단계로 구성했고, 프로젝트별 Ant·Maven·npm 빌드·배포 스크립트를 만들었습니다. 공통 기능을 구현한 뒤 여러 개발자의 변경을 어떻게 모아 배포할 것인지까지 연결한 작업입니다.

운영 확인에 필요한 로그는 MDC·Filter·Logback으로 서비스·사용자·업무별로 구분하고 기간·용량 기준 분할·압축 정책을 적용했습니다. 다만 이 구성이 모든 장애의 자동 탐지나 완전한 분산 추적을 제공했다는 의미는 아닙니다.

## 산출물은 기능 수보다 사용할 수 있는 경로였습니다

전문 처리의 재사용 구조, 인증 공통 기능, 개발 환경, 서비스별 배포와 로그 체계를 구축했습니다. 공통파트 PL로서의 결과는 제가 구현한 기능의 수만이 아니라, 다른 개발자가 자신의 업무를 개발하고 확인하는 데 사용할 기반을 제공한 것입니다.

다만 개발 리드타임·장애율·배포 실패율의 전후 측정값을 이 사례의 성과로 제시하지는 않습니다. 공통파트 PL의 책임을 24명 전원의 인사관리나 전체 프로젝트 총괄로 확대하지도 않습니다.

로컬 전문 연동 환경의 구체적인 경로는 이미 발행한 **‘외부기관 연동을 로컬에서 확인할 수 있게 만든 과정’**에서 다뤘습니다. 이 글은 그 내용을 반복하기보다, 해당 환경을 포함한 공통파트의 책임을 설명하는 상위 사례입니다. 같은 프로젝트의 배치 병렬화 성과도 별도 문제이므로 이 글에 기능 목록으로 덧붙이지 않습니다.

## 다음 공통 기능에서도 남길 기준

공통 기능은 내부 구현의 완성도와 함께 사용자가 접근할 경계가 명확해야 합니다. 이 경험을 통해 기능을 제공하는 일, 다른 개발자가 사용할 수 있는 형태로 정리하는 일, 운영에서 확인할 경로를 마련하는 일을 함께 보게 됐습니다.

현재 다시 검토한다면 공통 인터페이스 변경의 영향과 하위 호환성을 어떤 테스트로 확인할지까지 명시하겠습니다. 이는 당시 모든 호환성 테스트를 구축했다는 의미가 아니라, 이 경험 이후 더 분명하게 남기고 싶은 기준입니다.
