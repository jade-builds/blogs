## 연결 성공과 기능 호환은 다른 문제였습니다

현대오토에버에서 스마트팩토리 개발 프레임워크의 이기종 DB 전환을 담당했습니다. 사내 표준 DB 변경에 따라 MariaDB 중심으로 작성된 프레임워크를 MSSQL·MySQL·PostgreSQL에서도 사용할 수 있게 해야 했습니다. 전환 대응과 테스트 자동화 도입을 단독으로 수행했습니다.

이 프레임워크는 여러 프로젝트에서 재사용하는 기반이었습니다. 특정 DB에서 접속이 되거나 SQL 한 개가 실행되는 것만으로는 전환을 끝냈다고 보기 어려웠습니다. 제가 확인해야 할 대상은 **DB를 바꾼 뒤에도 공통 프레임워크 기능이 같은 업무 동작을 제공하는가**였습니다.

## SQL 문법과 그 SQL을 쓰는 기능을 함께 봤습니다

MariaDB 기준으로 작성된 데이터 접근 계층과 SQL을 검토하고, 대상 DB별 문법·함수 차이를 분석했습니다. 쿼리의 호환성을 확인하는 작업과 프레임워크 기능이 정상 동작하는지 확인하는 작업을 함께 수행했습니다.

문법 차이를 고쳤다는 설명만으로는 이 작업의 범위를 충분히 드러내기 어렵습니다. 제게 중요한 구분은 DB에 따라 달라질 수 있는 표현과, 그 표현을 사용하더라도 유지해야 하는 공통 기능의 동작이었습니다.

| 확인한 층위 | 작업의 의미 |
|---|---|
| 기존 MariaDB 데이터 접근 계층 | 특정 DB에 의존하는 쿼리와 함수 사용 확인 |
| MSSQL·MySQL·PostgreSQL의 쿼리 | 대상별 문법·함수 차이 분석과 호환성 확인 |
| 공통 프레임워크 기능 | DB 변경 후에도 기능이 동작하는지 검증 |
| 반복되는 확인 작업 | JUnit 기반 자동 검증 도입 |

이 표는 작업 범위를 정리한 것입니다. 모든 DB 기능을 포괄하는 호환성 인증표나 테스트 통과율을 뜻하지 않습니다.

## 반복할 확인을 수동 작업으로만 남기지 않았습니다

팀 최초로 JUnit 기반 자동화 검증을 도입했습니다. DB별로 변경 작업을 반복해야 하는 상황에서, 매번 사람이 기능을 다시 확인하는 방식에만 의존하지 않기 위한 선택이었습니다.

단순히 쿼리를 다른 문법으로 옮기는 일과, 옮긴 결과를 반복해서 확인할 수 있게 하는 일은 산출물이 다릅니다. 전자는 해당 변경을 가능하게 하고, 후자는 이후 수정에서도 기능을 다시 확인할 기반이 됩니다. 저는 DB 전환과 함께 이 검증 경로를 만드는 데까지 담당 범위를 넓혔습니다.

아래는 판단의 범위를 설명하는 개념도입니다. 실제 테스트 코드나 CI 실행 구성을 재현한 것은 아닙니다.

```text
MariaDB 기준 데이터 접근 계층·SQL 검토
    → 대상 DB별 문법·함수 차이 확인
    → 쿼리·프레임워크 기능 호환성 검증
    → JUnit 기반 반복 검증
```

## 전환 결과와 검증 범위를 구분합니다

MariaDB 기반 스마트팩토리 프레임워크를 **MSSQL·MySQL·PostgreSQL의 세 종류 DBMS에 대응하도록 전환하고, 쿼리·기능 호환성을 검증했습니다.** 기존 MariaDB에 더한 전환 대상이 세 종류라는 뜻입니다.

또한 수동 검증에 의존하던 변경 작업에 JUnit 자동화 검증을 도입했습니다. 이를 전체 테스트 커버리지 100%, 모든 SQL의 동일 성능, 운영 무중단 전환이나 CI의 DB별 자동 실행 완료로 확대하지 않습니다. 이 글에서는 테스트 수·통과율·실행 시간 개선율을 별도로 제시하지 않습니다.

## DB 경험을 검증 가능한 변경으로 이어갔습니다

이전 금융권 DB 운영에서 쿼리와 실행 구조를 살폈다면, 이 작업에서는 그 경험을 여러 DB를 사용하는 공통 프레임워크의 변경 검증으로 확장했습니다. DB를 다룬다는 공통점보다, **기존 동작을 유지해야 하는 변경에 반복 가능한 확인 수단을 붙였다는 점**이 중요한 경험이었습니다.

현재 이 작업을 다시 설계한다면 DB별 실제 실패 쿼리, 기대 결과, 회귀 테스트를 한 묶음으로 추적하겠습니다. 이는 당시 테스트 자산의 상세 구성을 그대로 재현한 것이 아니라, 이후 변경에 가져갈 기준입니다.
