## 데이터가 늘어나는 문제와, 그 데이터를 읽는 문제를 나눴습니다

다우기술 입사 초기 키움증권에서 약 200개 데이터베이스의 운영·관리를 수행했고, 이후 키움저축은행에서도 DB 운영과 테이블스페이스 관리, 로그성 테이블 관리, 쿼리 개선을 담당했습니다. 약 200개는 키움증권 업무의 범위이며 두 고객사 DB의 합계나 동시 운영 수를 뜻하지 않습니다.

이 글은 그중 로그성 데이터 증가에 대응한 저장 구조와 SQL 실행 구조 개선을 다룹니다. 용량을 확보하는 작업만으로 조회가 나아지는 것은 아니고, SQL 한 개를 고친다고 계속 늘어나는 데이터의 저장 문제가 사라지는 것도 아니었습니다.

## 로그성 테이블을 저장 공간과 조회 효율의 문제로 봤습니다

로그성 테이블 증가에 따른 저장 공간과 조회 성능 문제를 분석하고, Range Partition·Partition Index·Compression을 적용했습니다. 테이블스페이스 용량 관리와 함께, 증가하는 데이터 자체를 어떤 구조로 저장하고 조회할지 조정한 작업이었습니다.

여기서 중요한 구분은 저장 구조의 변경과 쿼리 변경을 같은 개선으로 뭉뚱그리지 않는 것입니다. 파티션·인덱스·압축을 적용한 대상과 SQL의 반복·연산 구조를 바꾼 대상은 각각 확인해야 합니다.

| 살핀 문제 | 적용한 변경 |
|---|---|
| 로그성 테이블 증가와 저장 공간 | Range Partition·Compression 적용 |
| 파티션 구조에 따른 인덱스 | Partition Index 적용 |
| 인덱스 컬럼에 걸린 연산 | 불필요한 컬럼 연산 제거 |
| 불필요한 인덱스·서브쿼리·동일 쿼리 반복 | Function Based Index와 쿼리 실행 구조 개선 |

이 표는 담당 업무의 변경 축입니다. 모든 조치를 단일 테이블·단일 장애에 동시에 적용했다는 의미는 아닙니다.

## 인덱스의 개수보다 쿼리가 실행되는 구조를 살폈습니다

인덱스 컬럼에 걸린 연산을 제거하고, 무분별하게 사용된 Function Based Index와 서브쿼리를 제거하거나 개선했습니다. 같은 쿼리를 반복 수행하는 서비스의 실행 구조도 개선했습니다.

제 접근을 ‘인덱스를 추가해서 빠르게 했다’고만 설명하면 중요한 부분이 빠집니다. **인덱스 컬럼에 어떤 연산이 걸려 있는지, 불필요한 쿼리 구조가 남아 있는지, 같은 SQL을 반복 호출하고 있는지**를 함께 살핀 경험이었습니다.

모든 함수 기반 인덱스나 서브쿼리가 잘못됐다는 결론은 아닙니다. 제가 개선한 것은 해당 업무에서 불필요하게 사용된 구조였습니다. 구체적인 실행 계획이 없는 상태에서 특정 접근 경로나 스캔 방식의 전환을 만들어 설명하지 않습니다.

## 결과는 운영과 개발을 함께 보는 기준으로 남았습니다

로그성 테이블의 저장 공간과 조회 효율을 개선하고, 컬럼 연산·불필요한 인덱스·서브쿼리·반복 SQL의 실행 구조를 정리했습니다. 저장 공간 절감률, 쿼리별 지연시간, 특정 기간의 장애 감소율은 이 사례의 수치로 제시하지 않습니다.

금융 연동의 조회 로직 약 95% 개선이나 인증 캐시의 Heap 감소 수치를 이 DB 운영 업무의 결과로 옮기지 않습니다. 이후 다른 프로젝트에서 SQL을 다루는 기반이 됐지만, 프로젝트의 성과 범위는 각각 구분합니다.

## 이후에는 애플리케이션의 호출 구조까지 봤습니다

DB 운영 경험을 통해 느린 요청을 볼 때 애플리케이션 코드와 저장 구조를 따로 떼어 보지 않게 됐습니다. 데이터가 어떤 속도로 쌓이고, 어떤 구조로 저장되며, 업무가 그 데이터를 몇 번 읽는지를 함께 살피는 기준이 생겼습니다.

현재 특정 튜닝 작업을 다시 검증한다면 변경 전후 실행 계획과 자원 사용량을 같은 SQL·부하 조건에서 비교하겠습니다. 이는 당시 모든 작업에 동일한 측정 자료를 확보했다는 주장이 아니라, 이 경험을 다음 개선에 적용할 때의 기준입니다.
