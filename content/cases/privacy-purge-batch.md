## 삭제 속도보다 먼저, 무엇을 어떤 순서로 처리할지 봤습니다

다우기술에서 키움저축은행 혁신금융 서비스의 개인정보 파기 배치와 스케줄러를 단독으로 개발했습니다. 한도조회·대출 연계 과정에서 수집한 데이터 중 보관 주기가 만료된 대상을 식별하고, 정해진 단계에 따라 이관·삭제하는 업무였습니다.

한도조회 서비스가 운영 중이었기 때문에, 삭제 SQL을 빠르게 실행하는 것만으로는 충분하지 않았습니다. 파기 대상을 올바르게 선정하고 처리 순서를 지키면서, 배치가 운영에 영향을 주는 시간과 DB 처리 범위를 함께 고려해야 했습니다.

## 같은 조건을 고객마다 다시 조회하고 있었습니다

기존 로직은 고객을 한 명씩 조회한 뒤, 해당 고객의 데이터를 관련 테이블에서 이관·삭제하는 방식이었습니다. 파기 과정은 세 단계로 나뉘었고, 여러 테이블에 걸쳐 유사한 SELECT·INSERT·DELETE가 반복됐습니다.

제가 주목한 것은 **고객은 달라도 각 단계에서 대상을 고르는 조회 조건이 같다는 점**이었습니다. 개별 SQL의 실행 계획만 고치는 것으로는 고객 수만큼 같은 경로를 다시 실행하는 구조가 남았습니다. 따라서 SQL 한 번의 비용뿐 아니라, 그 SQL을 업무 전체에서 몇 번 호출하는지를 변경 대상으로 봤습니다.

| 살핀 대상 | 변경한 방향 |
|---|---|
| 고객마다 반복하는 동일 조건 조회 | 단계별 대상 집합을 기준으로 조회 정리 |
| 고객별로 되풀이하는 이관·삭제 | 동일 조건의 SELECT·INSERT·DELETE를 단계별 통합 |
| 파기 단계와 여러 대상 테이블 | 단계별 이관·삭제 순서를 유지하면서 실행 구조 변경 |
| 운영 중인 한도조회 서비스 | 배치 실행 시간과 트랜잭션 범위를 함께 조정 |

## 고객 중심의 반복을 단계 중심의 처리로 바꿨습니다

각 단계에서 파기 대상 집합을 산정하고, 테이블별 이관·삭제를 통합하는 방향으로 처리 구조를 바꿨습니다. 핵심은 개인정보 파기 정책을 단순화한 것이 아니라, **같은 정책을 적용하는 과정의 불필요한 반복을 줄인 것**입니다.

아래는 실행 구조의 차이를 설명하는 개념도입니다. 실제 SQL, 트랜잭션 호출 경로, 커밋 횟수를 재현한 것은 아닙니다.

```text
변경 전
고객별 반복 → 단계별 대상 확인 → 관련 테이블 이관·삭제

변경 방향
단계별 대상 집합 산정 → 해당 단계의 테이블별 이관·삭제 통합
```

반복 호출을 줄이는 일과 트랜잭션 경계를 정하는 일은 구분했습니다. 처리 구조를 통합한다고 모든 파기 데이터를 하나의 거대한 트랜잭션으로 묶었다는 의미는 아닙니다. 운영 서비스 영향도를 고려해 실행 시간과 트랜잭션 범위를 조정했습니다.

## 결과는 실행 횟수의 재설계에서 나왔습니다

개인정보 파기 배치의 처리 시간을 **4시간에서 1.5시간으로 단축했습니다. 시간 감소율은 62.5%**입니다. 단순히 서버 자원을 늘리거나 병렬 실행만 추가한 사례가 아니라, 같은 조건으로 반복하는 DB 접근을 단계별 통합 처리로 바꾼 사례입니다.

이 수치는 파기 배치의 전후 소요 시간입니다. 동일 대상 건수·동일 부하의 통제 실험 결과나 모든 SQL의 성능 개선율로 확대하지 않습니다. 정확한 실행 횟수·락 대기 시간·커밋 횟수는 별도로 제시하지 않습니다.

2022–2023년 차세대 리뉴얼에서 수행한 ForkJoinPool 기반 배치 개선과는 다른 프로젝트입니다. 그때의 28분→9분대 결과를 이 파기 배치의 성과에 합치지 않습니다.

## 다음 배치에서도 먼저 물을 질문

이 경험 이후에는 느린 배치를 볼 때, 쿼리 하나의 속도와 쿼리를 반복하는 구조를 따로 살핍니다. 같은 조건을 반복 평가하고 있는지, 처리 대상을 집합으로 설명할 수 있는지, 처리 단위를 바꿀 때 이관·삭제 순서와 실패 경계는 어떻게 남아야 하는지가 먼저입니다.

현재 다시 점검한다면 단계 도중 실패했을 때의 재실행과 부분 완료 데이터의 처리까지 확인하겠습니다. 이는 당시의 실패 주입·재처리 테스트를 모두 완료했다는 주장이 아니라, 이 경험에서 이어진 후속 점검 기준입니다.
