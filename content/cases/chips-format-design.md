## 배치의 결과는 데이터가 아니라, 정해진 포맷의 전문이었습니다

다우기술에서 키움저축은행의 NICE 통계정보(CHIPS) 생성 배치를 개발했습니다. 전일 조회 고객 약 2만 명의 통계 데이터를 일 단위로 조회하고, NICE가 요구하는 포맷의 전문 텍스트를 생성하는 업무였습니다.

문제는 데이터를 한 번 출력하는 데서 끝나지 않았습니다. 오픈 직전에도 통계 항목의 추가·수정이 발생할 수 있었고, 생성한 텍스트를 검증 화면에서 다시 읽어 확인해야 했습니다. 그래서 **변경할 포맷과 그 포맷을 읽고 쓰는 로직을 어떻게 나눌 것인가**가 주요 설계 질문이 됐습니다.

## 문자열 조립 코드에 포맷을 흩어 놓지 않았습니다

전문을 문자열 이어붙이기로 구현하면 항목의 순서·길이·추가 여부가 생성 코드 안에 섞일 수 있습니다. 그 상태에서 검증 화면용 파싱까지 따로 만들면, 같은 포맷의 해석을 송신과 확인 경로에서 각각 관리하게 됩니다.

저는 Header·Body·Metadata VO를 분리하고, 각 라인의 메타데이터를 기준으로 전문 문자열을 생성하도록 구성했습니다. 핵심은 실제 데이터와 그 데이터를 전문으로 표현하는 포맷 정보를 나누는 것이었습니다.

| 구분 | 맡긴 책임 |
|---|---|
| Header·Body | 전문을 구성하는 데이터 표현 |
| Metadata | 각 라인의 포맷 정보 표현 |
| 메타데이터 기반 생성 | 데이터를 정해진 형식의 문자열로 구성 |
| 검증 화면용 파싱 | 생성 텍스트를 다시 읽어 확인할 수 있게 변환 |

이 구분은 당시 구조의 책임을 설명한 것입니다. 실제 클래스명·기관별 필드 길이·전문 양식을 재현한 표는 아닙니다.

## 생성과 파싱이 같은 포맷을 따르도록 했습니다

송신할 텍스트를 생성하는 기능과 검증 화면에서 그 텍스트를 확인하는 기능은 방향이 반대지만, 이해해야 할 포맷은 같았습니다. 그래서 생성과 파싱을 서로 무관한 문자열 처리 코드로 중복 구현하기보다, 직렬화 구조를 역직렬화에도 재사용할 수 있도록 설계·적용했습니다.

```text
책임 관계의 개념도

Header·Body 데이터 + Metadata 포맷 정보
    → 전문 텍스트 생성
    → 생성 텍스트 파싱
    → 검증 화면에서 확인

생성과 파싱에서 포맷을 해석하는 구조 재사용
```

이 그림은 실제 송수신 서버나 전체 검증 절차의 재현이 아닙니다. 생성과 확인이 같은 형식 정보를 바탕으로 연결된다는 점을 설명합니다.

## 바꾼 것은 포맷 변경이 닿는 범위였습니다

전일 조회 고객 약 2만 명 규모의 NICE 통계 전문 생성 배치를 구현했고, 오픈 직전의 추가 데이터·포맷 수정 요구에도 대응했습니다. Header·Body·Metadata의 분리와 생성·파싱 구조의 재사용이 그 기반이었습니다.

약 2만 명은 이 통계 배치의 대상 고객 규모입니다. 신용조회 연동의 일 처리 건수나 초당 처리량이 아닙니다. 이 사례의 결과를 코드 감소율·생성 시간 개선율·모든 전문의 무오류 보장으로 확대하지 않습니다.

생성한 텍스트를 다시 읽을 수 있다는 사실과 외부기관이 그 전문을 업무적으로 승인했다는 사실도 구분합니다. 모든 필드 조합의 왕복 변환 테스트나 기관 검증 통과율은 이 글에서 제시하지 않습니다.

## 다음 전문 설계에 가져간 기준

이 경험에서 얻은 기준은 포맷에 맞춰 출력하는 기능과, 그 출력을 해석하는 기능을 함께 보는 것입니다. 포맷이 두 경로에 흩어지면 변경할 때 서로 어긋날 수 있으므로, 바뀌는 정보와 재사용할 해석 책임을 먼저 나눕니다.

현재 다시 점검한다면 항목 길이·누락 값·포맷 버전 변경에 대해 생성과 파싱이 같은 기준을 따르는지 테스트하겠습니다. 이는 당시 모든 경계값 테스트를 완료했다는 설명이 아니라, 이 설계에서 더 구체화할 후속 검증 기준입니다.
